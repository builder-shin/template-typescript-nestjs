# Phase 5 실행 중 내린 룰링

SDD 실행 중 사용자를 대신해 내린 결정들이다. 각 항목은 무엇을 정했는지와 틀렸을 때의 비용을 함께 적는다.

- 계획: `docs/superpowers/plans/2026-08-30-phase5-put-upsert.md`
- 스펙: `docs/superpowers/specs/2026-08-28-nestjs-jsonapi-template-design.md` (5.3·6.2·7.2·15·16장)
- 브랜치: `phase-3-8-remaining` (Phase 5 구간: `96bc58e..41d8e18`)

1. Task 1과 Task 2를 한 번에 배치 dispatch한다 — 둘 다 브리프에 완전한 코드가 있고 파일이 겹치지 않으며, 2가 1의 산출물을 소비하지 않는다(소비자는 Task 3이다). 틀렸을 때 비용: 한쪽 결함이 나오면 두 커밋을 함께 되짚어야 한다.
2. 실행자의 브리프 이탈 3건을 모두 승인한다. 셋 다 린트/타입이 강제한 것이고 계약을 바꾸지 않는다. (1) `class Bare {}`가 `no-extraneous-class`에 걸린다 — 데코레이터가 없어 면제되지 않으므로 저장소의 기존 eslint-disable 관례로 처리. (2) `.into(model).values({...})`가 TS2353으로 막힌다(그 지점에서 `T`가 미해결 제네릭) — `.into<ObjectLiteral>(model)`로 해결, 캐스트 없음. **내 브리프의 "타입에서 막히기 쉬운 곳" 목록이 이것을 놓쳤다.** (3) `replacementValues` 테스트 콜백 7개가 `await` 없는 `async`라 `require-await`에 걸린다. 틀렸을 때 비용: 없음.
3. 미커버 방어 분기 4개 중 `upsertRow`의 `column === undefined` 하나만 테스트한다. `values`가 스키마와 무관한 자유 `Record`라 오탈자 프로퍼티를 넘기는 호출자가 실제로 도달시킨다 — 방어 코드가 아니라 **호출자 입력 검증**이다. 나머지 셋(`!Array.isArray(raw)`, row 모양, `inserted` 비-boolean)은 파킹한다: pg/TypeORM이 `RETURNING` 결과 모양을 깨는 실제 경로가 없어 DB를 목킹해야만 도달하고, 이 저장소는 DB 계층을 목킹하지 않는다. 틀렸을 때 비용: 드라이버가 언젠가 모양을 바꾸면 그 `TypeError`가 미검증인 채로 뜬다 — 조용히 틀리지는 않는다.
4. `orUpdate`가 DB 컬럼명을 받는다는 계약을 회귀로 지키는 테스트가 실질적으로 없었다. 기존 테스트가 쓰는 `title`·`body`는 프로퍼티명과 컬럼명이 같아, `orUpdate`에 프로퍼티명을 잘못 넘겨도 SQL이 동일해 통과한다. `publishedAt`(→ `published_at`)처럼 **이름이 갈리는** 컬럼으로 케이스를 더하되, 실행자에게 `updatable`→`properties` 바꿔치기로 **레드를 실측**하라고 요구했다 — 테스트가 계약을 붙잡는지가 이 수정의 전부이기 때문이다. 실측 결과는 예측과 달랐다: 조용한 무변경이 아니라 `QueryFailedError: column excluded.publishedAt does not exist`로 시끄럽게 죽었고, 주석을 실측에 맞게 고쳤다.
5. `replacementValues`의 "보낸 값 사용" 분기와 "결측 → 되돌림" 분기를 `status`(선언 기본값 `'draft'`) 한 쌍으로 가른다. nullable 컬럼 중 기본값이 null이 아닌 것이 없어 null 케이스만으로는 원리상 두 분기를 구분할 수 없다. 기존 null 케이스는 "명시적 `null`이 누락으로 취급돼 사라지지 않는다"는 별개 계약이라 남기되, 혼자서는 분기를 못 가린다는 것을 주석으로 적는다.
6. `getTargetValidationMetadatas`의 세 번째 인자가 상속 체인 워크를 켠다는 주석은 class-validator 0.15.1 기준 **사실이 아니다** — `groups` 없이 `strictGroups=false`로 부르는 이 사용 패턴에서는 그 인자 값과 무관하게 상속 워크가 항상 돈다. 인자는 그대로 두고 인과 서술만 정정하며, 실제 `extends` 상속 테스트를 더한다(있던 것은 중첩 스키마 합성 테스트뿐이라 상속과 다르다). 틀렸을 때 비용: 없음 — 동작은 원래 맞았다.
7. 브리프가 라우트 등록과 라우트 계약 테스트를 Task 3 몫으로 적었고 내 디스패치 메시지는 그것을 Task 4로 말했다. **브리프가 요구사항의 출처이므로 브리프가 이긴다** — 실행자가 브리프를 따른 것이 맞고 되돌리지 않는다. 틀렸을 때 비용: 없음(Task 4 브리프는 `examples-put.spec.ts` 하나만 만들어 중복이 없다).
8. `replace()`의 응답용 재조회를 **트랜잭션 안**에서 한다 — `create`/`update`는 커밋 뒤에 한다. `pg_advisory_xact_lock`이 트랜잭션 스코프라, 커밋 뒤 재조회는 잠금이 이미 풀린 다른 커넥션에서 돈다. "동일 ID 동시 요청을 직렬화한다"는 약속에 응답 본문이 포함되지 않게 된다. 형제와 다른 이유를 주석에 적어 다음 사람이 "일관성"으로 되돌리지 못하게 한다. 최종 리뷰가 이 결정을 diff에서 가장 잘 논증된 조각으로 꼽았다.
9. 클라이언트 생성 id 옵션(`allowClientGeneratedId`)을 `replace`에서 뺀다 — `parseResourceInput`은 `expectedId`가 주어지면 그 분기에 닿지 않으므로 죽은 코드였고, `update`가 이미 같은 패턴이다. id 불일치는 `expectedId` 갈래가 `ID_MISMATCH`로 계속 거부한다.
10. **계획 결함(Task 4 브리프):** "to-one 관계도 비운다"가 `PUT` 응답 본문의 `data.relationships.category.data`가 `null`이기를 단언하는데 통과할 수 없다. `replace`의 재조회는 요청이 **보낸** 관계만 include하고(create/update와 공유하는 기존 규약), 리셋된 관계는 정의상 보내지 않은 것이라 그 목록에 없다 — 시리얼라이저는 미로드 관계의 `data`를 아예 빼므로 값은 `null`이 아니라 `undefined`다. 형제 테스트가 이미 쓰는 `GET /relationships/{name}`으로 확인하도록 고친다. 대안(재조회에 스키마 소유 관계를 전부 include)은 `replace`의 응답 모양을 형제와 다르게 만드는 더 큰 계약 변경이라 택하지 않는다. 틀렸을 때 비용: `PUT` 응답 본문만 보는 클라이언트는 리셋을 응답에서 확인할 수 없다 — `create`/`update`와 같은 규약이고 JSON:API가 허용한다.
11. 브리프 밖 커밋(교차 스위트 경합 수정)을 수용한다. 실행자가 실측한 실제 결함이다 — `examples-api.spec.ts`의 **조건 없는 `DELETE`**가 새 스위트의 커밋된 행을 지우고, 반대로 새 스위트의 행이 그쪽의 **스코프 없는 카운트 단언**을 부풀렸다. 두 갈래 수정이 각각 다른 문제를 막는다: 스코프 한정 정리는 앞의 것을, 커밋 잠금은 뒤의 것을 — 후자는 정리를 아무리 좁혀도 남는다. 대안(카운트 단언을 접두사로 좁히기)은 `meta.total`처럼 스코프를 줄 수 없는 단언이 있어 택하지 않았다. 틀렸을 때 비용: 커밋하는 두 스위트가 서로 직렬화돼 그만큼 느려진다 — 나머지 스위트의 병렬성은 그대로다.
12. 동시성 테스트가 advisory 잠금을 검증하지 못한다는 실측(잠금 제거 후 2-way 8회·4-way 15회 전부 통과)을 받아들이되, **잠금은 유지하고 주석만 정정한다.** 원인은 `upsertRow`의 `ON CONFLICT` 문장이 트랜잭션의 첫 DB 접근이라 PostgreSQL의 행 잠금이 이미 두 트랜잭션을 끝까지 직렬화하기 때문이고, 현재 `replace()`가 upsert 앞에서 DB를 건드리지 않아 advisory 잠금이 더 벌어 주는 것이 없다. 빼지 않는 이유: 스펙 7.2가 요구하고, upsert **앞에** DB 접근이 하나라도 생기면 행 잠금은 너무 늦게 걸린다. 잠금 자체의 계약은 Task 2가 `pg_locks`로 검증한다. 틀렸을 때 비용: 없음 — 계약은 두 곳에서 지켜지고 주석만 사실과 맞게 된다.
13. 훅 실패 롤백이 `PUT`에 대해 테스트되지 않았다 — 브리프 첫 줄의 "계약"이 다섯 항목 중 하나로 적어 놓고 Step 1 코드에 넣지 않은 **브리프 결함**이고, 내 디스패치의 검토 목록도 같이 빠뜨렸다. `crud-transaction.spec.ts`에 `enableUpsert` 프로브를 더해 닫는다. 레드 실측: `afterSave` 호출을 지우니 `Expected: 500, Received: 201`.
14. **최종 리뷰가 잡은 결함 1 — 되돌림 사다리가 통째로 도달 불가능했다.** `upsert-executor.ts`의 `property in attributes`가 스키마 소유 프로퍼티 전부에 대해 항상 참이다: `tsconfig.json`의 `target: ES2023` → `useDefineForClassFields`가 true → 선택 필드가 진짜 클래스 필드로 방출되고, class-transformer가 `new targetType()`으로 인스턴스를 만들어 보내지 않은 필드도 `undefined`로 **존재**한다. 테스트가 초록이었던 이유는 `undefined` → TypeORM `DEFAULT` → `EXCLUDED`가 마이그레이션의 컬럼 DEFAULT를 집어와 `ExampleReplace`에 한해 답이 우연히 일치했기 때문이고, 단위 테스트가 운영이 절대 만들지 않는 **객체 리터럴**을 넘겨 이것을 볼 수 없었기 때문이다. Phase 2가 정확히 이 목적으로 만든 `presentKeys`(`create`/`update`는 이미 사용)를 `replace`만 버리고 있었다. `presentKeys.has(property)`로 고치고 단위 테스트를 `plainToInstance` 인스턴스 위에 다시 세운다. 레드 실측에서 **4개**가 실패했다 — 예상한 도달성 테스트 하나가 아니라 선택 필드의 되돌림이 통째로 깨져 있었다. 틀렸을 때 비용(고치지 않았다면): NOT NULL·기본값 없는 선택 필드를 선언한 자원이 `PUT`에서 의도한 `TypeError` 대신 Postgres 23502 → 날것의 500을 낸다.
15. **최종 리뷰가 잡은 결함 2 — 이번 단계가 스스로 플레이크를 심었다.** `upsert-executor.spec.ts`의 `pg_locks` 단언이 **클러스터 전역**을 세면서 `.toBe(0)`을 거는데, 이번 단계에 넣은 `acquireCommitLock`이 세션 수준 advisory 잠금을 두 스위트의 수명 내내 붙든다. 병렬 워커에서 터진다. 거울상인 `toBeGreaterThan(0)`은 남의 잠금으로도 통과해 검증하지 않는 것을 단언한다. 둘 다 `pg_backend_pid()`로 좁힌다. 3회 연속 그린은 반증이 아니다 — 타이밍 의존이고, 11번의 조건 없는 `DELETE` 사고와 같은 모양이다.
16. 실행자가 지시를 넘어 좁힌 `toBeGreaterThan(0)` → `toBe(1)`을 승인한다. pid로 좁히면 그 커넥션의 advisory 잠금 수가 정확히 알려지고(그 테스트에서 `upsertRow` 호출은 하나뿐), 재리뷰가 `withRollback`이 콜백 내내 커넥션 하나를 고정한다는 것과 `withMigrationLock`/`acquireCommitLock`이 전용 러너를 써 잠금을 흘리지 않는다는 것을 확인했다. 틀렸을 때 비용: 나중에 같은 커넥션에서 advisory 잠금을 하나 더 잡으면 이 단언이 깨진다 — 그것이 알고 싶은 신호다.
17. `replace()`의 훅 순서 차이를 코드가 아니라 **주석으로** 다룬다. `upsertRow`가 이미 INSERT한 뒤에 `beforeSave`가 도는데 `POST`는 반대라, 같은 트랜잭션에서 개수를 세는 훅이 `PUT`에서만 자기 자신을 센다. 순서를 바꾸면 "생성/교체 판정은 `ON CONFLICT` 문장이 한다"는 스펙 7.2와 충돌하므로 계약을 적는 쪽을 택한다.
18. 직렬화 실패 롤백 테스트는 `PUT`에 대해서만 단언한다. `create`/`update`는 커밋 뒤 재조회라 같은 상황에서 행이 살아남는데, 그 동작을 계약으로 굳히지 않는다 — 바람직해서가 아니라 아직 그런 것뿐이다.
19. 파킹: `create()`의 커밋 뒤 재조회로 인한 "직렬화 실패 시 커밋된 행 + 500"은 Phase 4의 기존 규약이라 이번에 건드리지 않는다. `replace()`는 전부 트랜잭션 안이라 이 문제가 없다.
20. 파킹: Nest가 `createHandleResponseFn`에 네 번째 인자를 넘기도록 바뀌면 `PUT` 생성이 조용히 200이 된다. 유일한 방어가 `examples-put.spec.ts`의 201 단언이지만 방어가 존재하므로 지금 조치하지 않는다.
21. Task 4의 범위 한정 재리뷰를 따로 돌리지 않고 Phase 5 최종 리뷰에 접는다 — 수정 4건이 전부 테스트 쪽이고 한 건은 레드가 실측됐으며, 최종 리뷰가 더 강한 모델로 같은 코드를 전부 읽는다. 최종 리뷰 브리프에 네 항목 검증을 명시적으로 넣었다.

## 이 단계가 남긴 교훈

Phase 3·4의 기록이 "결함은 조각 안이 아니라 **단계 경계**에 몰린다"고 적었다. Phase 5가 그 사례를 둘 더 냈고, 둘 다 조각별 리뷰를 모두 통과한 뒤 최종 리뷰에서야 잡혔다.

- **14번**: Phase 2가 만든 `presentKeys`를 Phase 5의 새 경로가 우회했다. 두 조각 모두 자기 자리에서는 옳았다 — 우회했다는 사실만이 결함이었고, 그것은 두 조각을 한꺼번에 볼 때만 보인다.
- **15번**: Phase 5가 넣은 테스트 픽스처(커밋 잠금)가 Phase 5가 넣은 다른 테스트(`pg_locks` 단언)를 깨뜨렸다. 같은 단계 안이지만 서로 다른 태스크였고, 각 태스크 리뷰는 자기 diff만 본다.

두 번째 교훈은 **테스트가 초록인 이유를 확인하라**는 것이다. 14번의 단위 테스트는 운영 경로가 절대 만들지 않는 입력 모양(객체 리터럴 대 `plainToInstance` 인스턴스)을 쓰고 있었고, 그래서 결함을 통과시켰다. 이 단계에서 실측 레드를 네 번 요구했고 그중 두 번은 예측이 틀렸다는 것을 드러냈다(4번의 "조용한 무변경"이 실제로는 시끄러운 실패, 14번의 "테스트 하나 실패"가 실제로는 넷). 주석이 실측보다 앞서 나간 사례도 네 건 정정했다.
