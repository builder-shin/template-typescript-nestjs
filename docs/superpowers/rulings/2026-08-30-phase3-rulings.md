# Phase 3 실행 중 내린 룰링

SDD 실행 중 사용자를 대신해 내린 결정들이다. 각 항목은 무엇을 정했는지와 틀렸을 때의 비용을 함께 적는다.

- 계획: `docs/superpowers/plans/2026-08-30-phase3-serializers-query-policy.md`
- 스펙: `docs/superpowers/specs/2026-08-28-nestjs-jsonapi-template-design.md` (4·8·15·16장)
- 브랜치: `phase-3-8-remaining` (Phase 3 구간: `0659173..5fac04f`, 25커밋)

1. Phase 3을 `phase-1-2-jsonapi-persistence`가 아니라 새 브랜치에서 진행한다 — 그 브랜치는 PR #2로 리뷰 중이고 커밋을 더하면 리뷰 대상이 바뀐다. 예전 브랜치 포인터는 `origin`과 같게 되돌렸고 계획 커밋은 새 브랜치에 그대로 있다. 틀렸을 때 비용: Phase 1-2가 병합된 뒤 이 브랜치를 rebase해야 할 수 있다(충돌 가능성 낮음 — 겹치는 파일은 `jest.config.js`와 `example.entity.ts`뿐).
2. 계획의 Step 1 테스트 원문이 약했던 것이므로 계획이 아니라 테스트를 고친다 — `toBeUndefined()`는 키 부재와 `links: undefined`를 구분하지 못하고, 관계의 links 생략 경로는 커버리지가 0이다. `resourcePath`를 선택으로 둔 설계의 핵심 계약이라 회귀 테스트 없이 넘기지 않는다. 틀렸을 때 비용: 테스트 두 개가 늘어날 뿐(구현 무변경).
3. 실행자가 짚은 두 우려 모두 계획의 오류이고 구현이 맞다. (1) FilterValue의 `| null`은 Interfaces 절에만 있던 잔재다 — `isNull`의 값은 참거짓 플래그이고 어떤 조건도 null을 값으로 갖지 않으므로 구현부(`| null` 없음)가 옳다. Task 10·11 브리프는 시그니처를 되풀이하지 않아 하류 오염 없음. (2) 테스트 개수 28은 오기, 실제 26. 계획을 고쳤다(커밋 별도). 틀렸을 때 비용: 없음 — 코드 무변경.
4. Task 6과 Task 7을 한 번에 배치 dispatch한다 — 둘 다 "브리프에 완전한 코드가 있는 순수 파서 + 전용 spec 파일"이라는 같은 모양이고, 파일이 겹치지 않으며 서로를 소비하지도 않는다. 리뷰는 한 단위로 본다. 틀렸을 때 비용: 한쪽에서 결함이 나오면 두 파일을 함께 되돌려야 한다(둘 다 신규 파일이라 되돌리기 쉬움).
5. Task 7 브리프의 "13 tests"는 오기, 실제 12개. 계획을 고쳤다(37d7099). 틀렸을 때 비용: 없음 — 코드 무변경.
6. 계획의 픽스처가 약했던 것이므로 구현이 아니라 픽스처를 고친다 — 네 정렬 필드가 모두 field===property라 `property: field`로 퇴행해도 통과한다. 사용자 입력이 열 이름이 되는 것을 막는 경계라 회귀 테스트 없이 넘기지 않는다(Task 1과 같은 종류). 틀렸을 때 비용: 픽스처 한 필드 이름 변경(구현 무변경).
7. 브리프의 "29 tests"는 오기, 실제 30개. 계획을 고쳤다. 틀렸을 때 비용: 없음 — 코드 무변경. (Task 5·7에 이어 세 번째 개수 오기 — 계획 작성 시 테스트 수를 눈으로 센 것이 원인이다.)
8. Important는 고친다 — 링크가 중복 파라미터를 잃으면 링크를 따라간 결과가 원래 페이지와 다른 집합이 되는데, 지금 테스트로는 루프가 통째로 사라져도 통과한다(Task 1·6과 같은 종류의 계획 결함). 틀렸을 때 비용: 테스트 하나 추가.
9. Minor(상한 100 허용 쪽)를 이미 여는 fix 라운드에 함께 넣는다 — 스킬은 minor를 루프에 넣지 말라고 하지만 그 취지는 라운드를 늘리지 말라는 것이고, 이미 도는 라운드에 3줄을 얹는 것은 라운드를 늘리지 않는다. 틀렸을 때 비용: 없음.
10. Task 9부터 실행자 dispatch에 "자기가 쓴 코드 중 어떤 테스트도 지나지 않는 분기를 보고하라"를 넣는다 — Task 1·6·8에서 같은 종류의 커버리지 갭이 세 번 나왔고 모두 계획의 테스트 블록에서 기인했다. 리뷰가 잡기 전에 실행자가 먼저 잡게 하는 편이 라운드를 줄인다. 틀렸을 때 비용: 실행자 보고가 조금 길어진다.
11. 갭1(`typeof sort !== 'string' || !Array.isArray(values)`) — 테스트를 더한다. 크래프팅된 커서로 도달 가능하고 신뢰할 수 없는 입력을 막는 가드다. 비용: 테스트 2개.
12. 갭2(`if (term === undefined) continue` 2곳) — 테스트가 아니라 코드에서 없앤다. 조밀 배열에서 도달 불가능한 죽은 분기이고, 계획이 준 `for` 루프 모양이 강요한 것이다. `forEach`는 콜백 인자를 `T`로 주므로 가드가 사라진다. 출력 문자열은 불변이며 기존 절 비교 테스트 4개가 그것을 고정한다. 비용: 출력이 달라지면 되돌린다(테스트가 즉시 잡는다).
13. 갭3(cursor 링크의 totals 분기) — 테스트를 더한다. 스펙 8.2가 "모든 링크가 page[totals]=true를 유지한다"고 정하는데 cursor 쪽만 비어 있었다. 비용: 테스트 1개.
14. 갭4(selfParams의 page[before] 분기) — 테스트를 더한다. 넷 중 가장 사용자에게 가깝다. 비용: 테스트 1개.
15. 파킹한다. `parsePage`의 불변식상 도달 불가능한 방어 분기이고, 없애려면 `PageRequest`를 판별 유니온(`{mode:'offset';number:number} | {mode:'cursor';after:string} | {mode:'cursor';before:string}`)으로 바꿔야 하는데 Task 11 브리프(750줄)가 현재 모양으로 이미 쓰여 있다. 커버리지 게이트(80%)를 위협하지 않는다. 틀렸을 때 비용: 방어 분기 두 개가 검증되지 않은 채 남는다 — 도달하면 빈 문자열/1페이지로 떨어지므로 무해한 방향이다. 최종 리뷰에 넘긴다.
16. Task 11은 opus로 dispatch한다 — 다른 태스크와 달리 실제 PostgreSQL과 TypeORM의 상호작용(take+leftJoinAndSelect의 두 질의 전략, 커서 파라미터의 타입 추론)에서 계획이 틀렸을 가능성이 남아 있고, 그 디버깅에는 상위 모델이 필요하다. 틀렸을 때 비용: 토큰이 더 든다.
17. 실행자의 계획 이탈 3건을 모두 승인한다.
18. `migrations.spec.ts`의 미한정 `pg_type`/`pg_indexes` 질의를 `public`으로 한정한 수정을 승인한다. 이 경합은 내가 Phase 1-2 리뷰에서 probe 스키마를 도입하며 심은 것이고(migration-revert.spec가 probe 스키마에 두 번째 example_status를 만든다), 워커 스케줄이 바뀌자 드러났다. 계획 밖 수정이지만 게이트를 초록으로 만드는 데 필요하고 원인 진단이 정확하다. 틀렸을 때 비용: 없음 — 질의가 보는 범위를 좁혔을 뿐이다.
19. 도달 가능한 미커버 분기 4건(gt/lt/lte 미실행, 비어 있지 않은 page[before]가 keyset 비교식을 만들지 않음, firstCursor 미단언, contains 이스케이프의 양성 검증 없음)은 고친다. page[before] 건이 가장 심각하다 — Phase 4의 prev 링크가 정확히 그 요청을 내보내는데 역방향 경로가 통째로 미검증이다. 틀렸을 때 비용: 테스트만 늘어난다.
20. 파킹한다. 없애려면 `PageRequest`를 판별 유니온으로 바꿔야 하는데, 그 변경은 Phase 4가 이 타입 위에 무엇을 얹을지 정한 뒤가 낫다. 틀렸을 때 비용: 방어 분기가 검증되지 않은 채 남는다(도달 시 무해한 기본값으로 떨어진다).
21. Task 11의 태스크 리뷰를 구현 라운드 뒤가 아니라 fix 뒤에 한 번, 구간 전체(bfac0b9..46f3cef)로 돌린다 — 실행자가 갭을 선제 보고해 리뷰 전에 fix를 먼저 돌렸기 때문이다. 최종 상태를 한 번 보는 것이 구현과 fix를 따로 보는 것보다 커버리지가 넓다. 틀렸을 때 비용: fix가 구현을 망가뜨렸다면 같은 리뷰가 잡는다(같은 diff 안에 있다).
22. Important를 고친다. 리뷰어가 TypeORM 소스(`computeCountExpression`)를 직접 읽고, 1.1의 `getCount()`가 조인이 있으면 `COUNT(DISTINCT alias.id)`를 쓴다는 것을 확인했다. 즉 내 주석 "조인 뒤에 세면 부푼다"는 이 버전에서 사실이 아니고, 그것을 지킨다는 테스트도 순서를 강제하지 못한다. 순서 자체는 옳지만(비용 문제) 근거가 틀렸다 — 템플릿이 틀린 모델을 가르치면 베껴 쓰는 쪽이 그것을 물려받는다. 주석과 테스트 이름을 실제 동작에 맞춘다. 틀렸을 때 비용: 없음 — 동작 무변경, 문서 정정.
23. Minor(`escapeLike`의 `\` 미검증)를 같은 라운드에 함께 넣는다. 실행자가 수동 프로브로 이미 확인한 것을 테스트로 남기는 것뿐이다.
24. 최종 전체 리뷰의 범위를 `main`과의 merge-base(5193bf5)가 아니라 Phase 1-2의 head(0659173)부터로 좁힌다 — merge-base 기준이면 54커밋 737KB가 되는데 그중 28커밋은 PR #2에서 이미 리뷰 중인 Phase 1-2다. 이미 게이트를 지난 작업에 최종 리뷰 예산을 쓰지 않는다. 틀렸을 때 비용: Phase 1-2와 Phase 3의 접합부에서만 드러나는 문제를 최종 리뷰가 놓칠 수 있다 — 다만 Task 4·11이 실제 PostgreSQL 게이트를 통째로 돌려 그 접합부(엔티티·마이그레이션·fixture)를 이미 지났다.
25. 여섯 건 모두 고친다. Important는 Phase 4가 배선할 계약이고 양쪽이 다 틀렸다. Minor 다섯은 각각 (a) undefined/null 관계 계약 미고정 (b) defaultPageSize 미검사 (c) contains를 비문자 필드에 선언하면 400이 아니라 500 (d) assertCursorSortable이 COUNT 뒤에 돈다 (e) 호출자 없는 export — 전부 작고, 스킬이 정한 대로 한 번의 fix wave로 묶는다. 틀렸을 때 비용: wave가 무언가를 깨뜨리면 scoped 재리뷰가 잡는다.
26. `parseQuery`의 세 번째 인자를 `declaredRelationships: readonly string[]`에서 시리얼라이저로 바꾸자는 리뷰어의 제안은 받지 않는다 — 결함이 아니라 설계 개선 제안이고, 그 인터페이스의 소비자(Phase 4 컨트롤러)를 쓰기 직전에 시그니처를 흔들 이유가 없다. Phase 4로 넘긴다. 틀렸을 때 비용: 두 선언이 어긋날 여지가 한 단계 더 남는다(다만 include 파서가 양쪽 교집합을 이미 강제한다).
27. `collectIncluded`가 아직 src/에서 호출되지 않는 것을 결함으로 보지 않는다 — 리뷰어 판단대로 "included에 무엇이 실리는가"는 스펙 4장이 시리얼라이저 계층에 준 책임이고, Phase 4로 미루면 JSON:API의 (type,id) 중복 금지 규칙이 컨트롤러로 샌다. parseQuery·buildOffsetLinks·buildCursorLinks도 같은 상태다.
