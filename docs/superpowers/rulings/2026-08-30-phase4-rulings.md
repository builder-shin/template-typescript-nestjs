# Phase 4 실행 중 내린 룰링

SDD 실행 중 사용자를 대신해 내린 결정들이다. 각 항목은 무엇을 정했는지와 틀렸을 때의 비용을 함께 적는다.

- 계획: `docs/superpowers/plans/2026-08-30-phase4-crud-actions.md`
- 스펙: `docs/superpowers/specs/2026-08-28-nestjs-jsonapi-template-design.md` (4·5.3·6·7·16장)
- 브랜치: `phase-3-8-remaining` (Phase 4 구간: `6442263..b7ea563`)

1. Task 8은 단위 테스트 없이 통과시킨다 — 그 파일은 이미 각자 테스트된 조각들을 잇는 배선이고, 흉내로 검증하면 흉내가 맞는지를 검증하게 된다. 실제 계약은 Task 10이 진짜 HTTP와 진짜 PostgreSQL로 확인한다(스펙 15장이 "DB 없는 컨트롤러 단위 테스트로 계약을 대체하지 않는다"고 정한 것과 같은 이유). 틀렸을 때 비용: Task 8의 결함이 Task 10에서야 드러나 되짚어야 한다 — 두 태스크가 붙어 있어 되짚는 거리가 짧다.
2. `relationshipsSchema`를 클래스가 아니라 선언 객체로 둔다. 스펙 6.1의 예시는 클래스지만, 클래스로는 6.3이 요구하는 "필드 이름의 교집합"을 런타임에 읽을 수 없고(초기값 없는 선언 필드는 인스턴스에 없다) linkage를 행으로 해석하는 데 필요한 대상 엔티티를 들고 있을 자리도 없다. 옵션 이름은 스펙 그대로 둔다. 틀렸을 때 비용: 스펙 문서와 코드의 모양이 달라 보인다 — 계획과 코드 주석에 근거를 남겨 상쇄한다.
3. prefix 검증을 팩토리가 아니라 베이스 생성자에서 돌린다. 스펙 6.1은 "팩토리가 조립 시점에" 비교하라고 하지만, 팩토리는 `@Controller`가 붙기 전에 돌아 그 시점에는 비교할 경로가 없다. 생성자로 옮기면 부트스트랩에서 터지므로 "잘못된 링크가 조용히 나가는" 상황은 그대로 막힌다. 틀렸을 때 비용: 실패가 import 시점이 아니라 앱 기동 시점에 난다.
4. `documents.ts`를 스펙 6.2의 7개 concern 목록 밖에 하나 더 둔다. 다섯 액션과 관계 액션이 모두 같은 응답 모양을 만드는데 각자 리터럴을 쓰면 `included`가 빌 때의 처리가 라우트마다 갈린다. 틀렸을 때 비용: concern 파일이 하나 는다.
5. `upsert-executor.ts`(스펙 6.2의 7번째 파일)와 `PUT` 라우트는 Phase 5의 계획이 맡는다. 이 계획의 `enableUpsert`는 선언만 받아 두고 라우트를 만들지 않으며, `replaceSchema` 없이 켜면 조립 시점에 던진다. 틀렸을 때 비용: Phase 4만으로는 스펙 16장의 `PUT` 행이 비어 있다.
6. 브리프 Step 4의 catch 스니펫이 기존 주석 두 개(로그의 요청 식별자, pin-before-set 순서)를 지우고 있었다 — 계획 결함이다. 둘 다 **왜**를 적은 것이라 복원한다(addf2b0). 틀렸을 때 비용: 없음 — 주석만 되돌렸고 로직 무변경.
7. `catch`의 `first === undefined` 가드는 파킹한다. 없애려면 `normalize`가 비어 있지 않은 튜플을 돌려줘야 하는데 `JsonApiErrors.errors`와 `flatten`의 결과가 모두 일반 배열이라 어딘가에서 같은 런타임 좁히기가 필요하다. 틀렸을 때 비용: 방어 분기 하나가 미검증으로 남는다(도달하면 500).
8. `toJsonApiError`가 `failure.property`만 써서 중첩 필드의 pointer가 부모를 잃는다 — `{child:{name:''}}`가 `/data/attributes/name`을 가리켜 존재하지 않는 최상위 필드를 고치라고 말한다. 계획 결함이다. 중첩 처리를 지우는 것(YAGNI)이 아니라 경로 누적으로 고치고 테스트로 덮는다 — 지우면 자식만 틀린 경우 오류가 0개가 되어 `JsonApiErrors([])`가 TypeError를 던지고 500이 나간다. 이 결함이 안 보인 이유가 분기 5건이 미커버인 것과 같은 뿌리(중첩 스키마 부재)다. 틀렸을 때 비용: 중첩 스키마가 영영 안 생기면 쓰이지 않는 코드가 남는다 — 템플릿 소비자가 객체 값 attribute를 추가하는 것은 흔한 일이라 낮게 본다.
9. 분기 4·5(`constraints ?? {}`, `detail ?? 기본값`)는 파킹한다. class-validator가 언제나 메시지를 채운다는 것은 라이브러리 내부 사정이지 공개 계약이 아니다. 도달하면 무해한 기본값으로 떨어진다.
10. Task 3과 Task 4를 한 번에 배치 dispatch한다 — 둘 다 "브리프에 완전한 코드가 있는 순수 모듈 + 전용 spec"이고 파일이 겹치지 않으며 4가 3을 소비하지 않는다. 리뷰는 한 단위로 본다. 틀렸을 때 비용: 한쪽 결함이 나오면 두 커밋을 함께 되짚어야 한다.
11. 실행자의 이탈 2건을 승인한다. (1) `applyAttributes<T extends object>`의 제네릭을 `entity: object`로 낮춘 것 — T가 한 곳에만 쓰여 `no-unnecessary-type-parameters`에 걸린다. 동작 무변경. (2) `Array.isArray(path) ? path[0] : path`가 `any`를 흘려(`Array.isArray`가 `unknown`을 `any[]`로 좁힌다) `const entries: unknown[]` 패턴으로 다시 쓴 것 — `serializer.ts`의 `linkage()`와 같은 방식이다. 틀렸을 때 비용: 없음 — 둘 다 린트가 강제한 형태 변경이고 계약은 그대로다.
12. Istanbul이 못 보는 갭 2건을 처리한다. (1) `raw === '/'` 갈래는 스펙 5.1이 다루는 루트 마운트 컨트롤러의 실제 입력이므로 테스트를 더한다. (2) `withLeading.length > 1`은 위 가드 때문에 거짓이 될 수 없는 죽은 조건이므로 지운다 — 기존 끝-슬래시 테스트가 동작을 고정한다. 틀렸을 때 비용: (2)가 사실 도달 가능했다면 기존 테스트가 즉시 실패한다.
13. 미커버 분기 3건(resolveOne의 `row === undefined`, resolveRelationships의 cardinality-배열 모양 TypeError 2건)을 파킹한다. 셋 다 TypeScript가 불변식을 증명하지 못해 남는 좁히기 가드이고, `parseLinkageInput`의 반환 모양이 같은 `rule.cardinality`로 이미 결정돼 있어 도달할 수 없다. Task 1의 `first === undefined`와 같은 부류다. 틀렸을 때 비용: 도달하면 TypeError로 시끄럽게 죽는다(조용히 잘못된 데이터를 쓰지 않는다).
14. Task 6과 Task 7을 배치 dispatch한다 — 6은 `query.ts`+`documents.ts`, 7은 `route-registrar.ts`로 파일이 겹치지 않고 7이 6을 소비하지 않는다. 7이 이 계획에서 가장 까다로운 태스크(동적 데코레이터)이므로 같은 실행자가 6으로 손을 푸는 이점도 있다. 틀렸을 때 비용: 7에서 막히면 6도 함께 되짚어야 한다 — 6은 독립 파일이라 되짚는 비용이 낮다.
15. 실행자의 브리프-린트 충돌 최소 수정 5건을 모두 승인한다. 그중 5번은 내 브리프의 실제 버그였다 — 테스트 헬퍼의 `writeGuards?: CanActivate[]`가 실제 계약(`Type<CanActivate>[]`, 인스턴스가 아니라 클래스)과 달라 tsc가 거부했다. 나머지 넷(`host.prototype`의 any 누출을 타입 프레디케이트로, 미사용 클래스 삭제, 반환 타입 명시, `!` 제거)은 전부 전역 제약이 강제한 것이다. 틀렸을 때 비용: 없음 — 계약은 그대로다.
16. 미커버 분기 4건 중 2건을 고친다.
17. 나머지 2건은 파킹한다. 방어용 TypeError 3건(도달 불가), 관계 델리게이트 본문(Task 8이 구현하고 Task 10의 wire 테스트가 증명 — 지금 등록만 확인하는 것이 맞다).
18. Task 8을 opus로 dispatch한다 — 앞선 여섯 태스크의 조각을 전부 잇는 유일한 파일이고, 계획이 미리 짚은 세 가지 타입 난점(`create()`의 인자, `Reflect.get`의 any, 관계 규칙 인덱싱)이 실제로 걸릴 자리다. 틀렸을 때 비용: 토큰이 더 든다.
19. 실행자의 브리프 교정 4건을 모두 승인한다.
20. 커버리지 게이트가 Task 10까지 빨간불인 것을 받아들인다. 게이트를 통과시키려고 조립 파일에 흉내 테스트를 넣지 않는다 — 그것이 계획이 Task 8에 단위 테스트를 두지 않기로 한 이유와 정확히 충돌한다. 틀렸을 때 비용: Task 9·10이 끝나기 전에 이 브랜치를 보는 사람이 게이트 실패를 자기 변경 탓으로 오인할 수 있다. 실행자가 같은 우려를 보고했다.
21. 리뷰어가 제안한 (b)를 택한다 — `parseRelatedCollectionQuery`가 `page[totals]`를 받아들이되 무시한다. (a)(`totals:false`로 링크 생성)를 택하면 `last` 링크가 사라진다. 스펙 8.2는 이 엔드포인트가 총 개수와 페이지 링크를 낸다고 정하므로 `last`를 잃는 쪽이 손해다. 틀렸을 때 비용: 이 엔드포인트에서 `page[totals]=false`를 보내도 총 개수가 나온다 — 스펙이 "언제나 낸다"고 정했으므로 의도대로다.
22. Important 1(관계 대상 id가 uuid 모양이 아니면 500) — 고친다. `assertIdShape`가 경로 id만 막고 본문 linkage의 id는 그대로 PG로 가서 22P02 → 500이 된다. 카탈로그의 의도된 답은 404다. 두 곳이 같은 규칙을 쓰도록 `canIdentify`를 리졸버에 두고 `crud-actions`가 재사용한다. 틀렸을 때 비용: 없음 — 가리킬 수 없는 id는 정의상 없는 자원이다.
23. Important 2(두 선언의 cardinality 드리프트 미검출) — 고친다. 어긋나면 `showRelatedFor`가 배열을 to-one 분기로 넘겨 500이 난다. 이 파일은 이미 `enableUpsert`·`resourcePath` 정합성을 조립 시점에 던지므로 같은 자리에 둔다.
24. Minor (a)(`readLinkage`/`isRelationshipInput`이 `parseLinkageInput`의 검사를 문구까지 중복)와 (b)(`linkageLinks`가 시리얼라이저의 링크 조립을 중복) — 이미 여는 라운드에 함께 넣는다. 둘 다 리뷰어가 "갈릴 여지"로 짚은 중복이고, (a)는 본문이 객체가 아닐 때 pointer가 두 곳에서 다르던 것도 함께 없앤다.
25. Minor(`UUID_PATTERN`이 `filter.ts`와 중복) — 파킹한다. 그쪽은 필터 값의 형식을, 이쪽은 행을 가리킬 수 있는가를 본다. 지금 합치면 리졸버가 필터에 의존하게 된다.
26. Task 9와 Task 10을 배치 dispatch한다 — 10은 9 없이는 돌 수 없고(라우트가 없다), 9의 배선 결함은 10에서 즉시 드러난다. 따로 돌리면 9의 리뷰가 "라우트는 등록됐다"까지만 보고 배선이 실제로 동작하는지는 못 본다. 틀렸을 때 비용: 두 커밋을 함께 되짚어야 한다.
27. 브리프의 오류 2건(둘 다 Task 9, 내 실수)에 대한 실행자 처리를 승인한다.
28. 실행자가 보고한 `truncateAll` 경합을 닫는다. Task 10이 `public`에 커밋하는 첫 스펙이 되면서, `migrations.spec.ts`의 `afterAll` TRUNCATE가 다른 워커의 커밋 행까지 지우고 ACCESS EXCLUSIVE로 읽기를 막는 위험이 됐다. 그 describe는 전부 `withRollback`이라 지울 것이 없는 방어 코드다. 9회 연속 초록은 창이 좁다는 뜻이지 없다는 뜻이 아니다. 틀렸을 때 비용: 없음 — 지울 것이 없었다면 제거 후에도 통과한다(그것을 확인 조건으로 걸었다).
29. README 갱신(브리프 마무리 절)을 이 라운드에 함께 넣는다. 실행자가 지시대로 하지 않았다고 보고했고, `test/docs/readme.spec.ts`가 경로 존재만 보므로 게이트는 초록이었다 — 게이트가 잡지 못하는 문서 드리프트다.
30. Important를 고친다. "관계 대상을 못 찾으면 자원도 만들지 않는다"는 트랜잭션 경계를 증명하지 못한다 — `resolveRelationships`가 `save()` 전에 끝나므로 트랜잭션 래퍼를 지워도 통과한다(리뷰어 지적). 그런데 `crud-base.ts`의 `afterSave` 주석은 "여기서 던지면 저장도 함께 롤백된다"를 문서로 약속하고, 그 계약을 덮는 테스트가 하나도 없다. 저장 **뒤에** 터지는 경로(훅이 던지는 프로브 컨트롤러)만이 경계를 증명한다. 틀렸을 때 비용: 프로브 앱 조립이 늘어난다 — `route-registrar.spec.ts`에 선례가 있다.
31. Minor 1(204 본문 없음이 넷 중 둘만 고정)과 Minor 2(README API 예시 절 누락)를 같은 라운드에 넣는다. 라운드를 늘리지 않는다.
32. `@ValidateIf((_, v) => v !== undefined)`로 "없어도 됨"과 "null 허용"을 가른다. `@IsOptional()`은 컬럼이 실제로 nullable인 곳(`body`, `publishedAt`)에만 남긴다. 템플릿 소비자가 `ExampleUpdate`를 그대로 베끼므로 근거 주석도 넣는다. 틀렸을 때 비용: 없음 — 500이던 것이 422가 된다.
33. Important 1(관계 DELETE가 협상을 빠져나감) — 판정 기준을 메서드가 아니라 둘로 가른다: (a) Content-Type을 보냈으면 메서드와 무관하게 vendor 타입이어야 한다, (b) 본문을 요구하는 메서드는 Content-Type이 필수다. `BODY_METHODS`에 DELETE를 그냥 더하면 본문 없는 `DELETE /examples/{id}`가 415가 된다는 리뷰어 경고를 그대로 반영했다.
34. Important 2(시리얼라이저만 선언한 관계가 라우트 없이 링크만 냄) — 읽기 라우트를 살린다. 리뷰어의 스펙 6.3 독해에 동의한다: 교집합 규칙의 근거절이 "**쓰기** 관계 라우트"로 좁혀져 있고, 앞 문단은 시리얼라이저 선언에서 읽기 라우트를 만든다. 반대쪽(주석만 고치기)을 택하면 시리얼라이저가 라우트 등록 결과를 알아야 하는데 그것은 스펙 4장의 계층 소유권을 깬다. 틀렸을 때 비용: 읽기 전용 관계에 라우트 두 개가 더 생긴다 — Example은 두 관계가 모두 쓰기라 공개 표면 불변.
