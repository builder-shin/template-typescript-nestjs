# Phase 7: BullMQ 잡 — `processExample`과 `purgeExpiredRefreshSessions` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 백그라운드 잡 두 개를 실제 Redis와 실제 PostgreSQL 위에서 돌리되, API 프로세스는 broker를 전혀 모르게 둔다.

**Architecture:** `@nestjs/bullmq`를 쓰지 않는다. 순수 `bullmq`와 독립 워커 진입점(`src/app/jobs/worker.ts`)을 쓰고, 워커가 `data-source.ts`와 같은 방식으로 자기 `DataSource`를 만든다. 스케줄러 의존성을 더하지 않는다 — 외부 cron이 enqueue만 한다.

**Tech Stack:** TypeScript 6.0.3(ESM, `strict` + `noUncheckedIndexedAccess`), NestJS 12, TypeORM 1.1.0, bullmq 6.3.4, ioredis 5.11.1, PostgreSQL 18, Redis 8, Jest 30

**Spec:** `docs/superpowers/specs/2026-08-28-nestjs-jsonapi-template-design.md` (3 디렉터리 구조, 10 비동기 작업, 12 설정과 환경 변수, 13.1 npm scripts, 15 테스트 전략)

## 사전 검증 결과 (계획 작성 중 실측)

전문은 `.superpowers/sdd/phase7-probe-findings.md`.

1. **의존성:** `bullmq@6.3.4`, `ioredis@5.11.1`. ioredis를 5.x로 고정한 이유는 `typeorm@1.1.0`이 `ioredis ^5.0.4`를 optional peer로 선언하기 때문이다(6.0.0으로 자동 해결되면 peer가 어긋난다). `pnpm-workspace.yaml`의 `allowBuilds`에 `msgpackr-extract: false`를 더해야 한다 — 없으면 `pnpm install`이 `ERR_PNPM_IGNORED_BUILDS`로 exit 1이 되어 CI의 `--frozen-lockfile`이 깨진다. msgpackr은 순수 JS로 폴백한다(소스와 `.node` 부재로 확인).
2. **`@nestjs/bullmq`를 쓰지 않는다 — 실측 근거가 있다.** 실제 `AppModule`에 `BullModule.forRootAsync`(`REDIS_URL`을 읽는)를 넣어 보니 무관한 `health.controller.spec.ts`의 11개 중 10개가 즉시 실패했다. `test/app-factory.ts`가 `AppModule`을 통째로 import하는 유일한 조립 지점이라, 그 그래프 어디에든 Bull 등록이 있으면 **스위트 전체가 Redis를 요구하게 된다.** 스펙 12장의 "API는 broker를 import하지 않는다"는 이 사실을 미리 말하고 있었다. 순수 `bullmq` + 독립 스크립트는 새 의존성도, `@Module`도 없어서 실수로 `AppModule`에 배선될 경로 자체가 없다.
3. **Redis는 지금 테스트 게이트에 없다.** `docker-compose.test.yml`에 redis 서비스가 없고 `check.sh`는 `db`만 띄운다. 기존 `db` 블록과 같은 모양으로 나란히 추가해야 한다.
4. **재시도 의미론:** 평범한 `Error`는 `attempts`까지 재시도된다(`attempts: 3`에서 프로세서가 3번 불리는 것을 실측). `bullmq`가 export하는 `UnrecoverableError`는 `attempts`를 무시하고 한 번에 영구 실패시킨다.
5. **`SKIP LOCKED`는 FK cascade 잠금을 막아 주지 않는다.** 오직 `lock_timeout`만 막는다(500ms에서 55P03을 유도해 확인). 스펙 10장의 주장이 실측으로 확인됐고, 그래서 `lock_timeout`이 선택이 아니라 필수다. 동작이 확인된 문장:
   ```sql
   SET LOCAL lock_timeout = '500ms';
   DELETE FROM refresh_sessions WHERE id IN (
     SELECT id FROM refresh_sessions WHERE expires_at < $1
     ORDER BY expires_at FOR UPDATE SKIP LOCKED LIMIT $2
   ) RETURNING id;
   ```
6. 의존성 설치 후 `./scripts/check.sh`가 초록이다(56 스위트 / 748 테스트).

## 이 계획이 내리는 설계 결정

- **테스트 게이트에 Redis를 넣는다.** 스펙 10장이 "일시적 DB 오류는 최대 3회 재시도"를 계약으로 정하는데, 그 계약은 BullMQ 없이 확인할 수 없고 BullMQ는 Redis 없이 돌지 않는다. 이 저장소는 인프라를 목킹하지 않는다(스펙 15장). 재시도 계약을 주장만 하고 검증하지 않는 것은 이 저장소가 반복해서 잡아 온 바로 그 실수다. 비용은 `check.sh`마다 alpine 컨테이너 하나가 더 뜨는 것이다.
- **잡 핸들러는 큐를 모른다.** 각 핸들러는 `EntityManager`(또는 `DataSource`)와 페이로드만 받는 평범한 함수다. BullMQ의 `Job`을 인자로 받지 않는다 — 그러면 계약을 확인하려고 `Job`을 흉내 내야 하고, 흉내가 맞는지를 검증하게 된다. 큐와 핸들러를 잇는 것은 워커 진입점의 일이다.
- **"경고 후 종료"는 성공이지 실패가 아니다.** 잘못된 UUID와 없는 Example은 재시도해도 답이 달라지지 않는다. 핸들러는 경고를 남기고 **정상 반환**한다 — 그래서 `UnrecoverableError`가 필요 없다. 반대로 일시적 DB 오류는 그대로 던져 BullMQ가 재시도하게 둔다.
- **`purgeExpiredRefreshSessions`는 배치마다 커밋한다.** 한 트랜잭션으로 전부 지우면 긴 잠금이 걸리고, 중간에 실패하면 한 행도 못 지운다. 배치마다 커밋하면 실패해도 이미 지운 것은 남고 재시도가 이어서 한다.
- **워커는 Nest 애플리케이션 컨텍스트를 만들지 않는다.** HTTP도 컨트롤러도 필요 없고, `AppModule`을 부팅하면 API의 설정 요구(`JWT_SECRET_KEY` 등)까지 워커가 지게 된다. `data-source.ts`가 이미 하는 대로 `DataSource`만 직접 만든다.

## Global Constraints

- 모든 상대 import에 `.js` 확장자를 붙인다. 빠뜨리면 `tsc`가 `TS2835`로 거부한다.
- `noUncheckedIndexedAccess`가 켜져 있다. `!`나 `as`로 지우지 말고 실제 분기로 좁힌다.
- ESLint는 `strictTypeChecked` + `stylisticTypeChecked`다. `any`가 흘러나오는 표현은 전부 오류다. 숫자를 템플릿 리터럴에 넣을 때는 `String(x)`로 감싼다. `obj['key']`는 `dot-notation`이 막는다.
- 함수 선언에는 명시적 반환 타입을 붙인다.
- 오류는 `JsonApiError`(사용자 입력)와 `TypeError`(프로그래밍·선언 오류)만 던진다. **잡에는 HTTP 사용자가 없으므로 `JsonApiError`를 쓸 자리가 없다** — 재시도시킬 오류는 그대로 흘려보내고, 재시도해도 소용없는 입력은 경고 후 정상 종료한다.
- **API 프로세스는 `bullmq`를 import하지 않는다.** `src/config/app.module.ts`가 닿는 그래프 어디에도 broker가 들어가면 안 된다. 스펙 12장의 계약이고, 실측으로 확인된 실패 모드다.
- 애플리케이션 코드에 암묵적 기본값을 두지 않는다(스펙 12장).
- 이 프로젝트의 ESM Jest 설정은 `jest` 전역을 주입하지 않는다 — `jest.fn()`/`jest.mock()`/`jest.useFakeTimers()`를 쓸 수 없다.
- 테스트는 `TRUNCATE`나 조건 없는 `DELETE`를 쓰지 않는다. 커밋하는 스위트는 자기 접두사만 지운다.
- SQLite 대체 경로를 넣지 않는다.
- 주석과 테스트 이름은 한국어로 쓰고 **왜**를 적는다.
- 커밋 메시지에 AI 관련 트레일러를 넣지 않는다. 저장소 소유자의 명시적 규칙이다.
- 모든 단계가 끝나면 `./scripts/check.sh`가 통과해야 한다.

  ```ts
  // src/config/broker.ts

  export function brokerConnection(redisUrl: string): ConnectionOptions;
  ```

**왜 `broker.ts`가 따로 있는가:** 스펙 3장이 `src/config/broker.ts`를 "Redis/BullMQ 연결 설정"의 자리로 지정한다. 연결을 만드는 코드가 한 곳에 있어야 큐(생산자)와 워커(소비자)가 같은 옵션을 쓴다 — 두 곳에서 각자 만들면 한쪽만 고쳐지는 날이 온다.

**연결 옵션은 실측된 모양이다.** BullMQ는 `connection`에 `{ url }`을 그대로 받는다 — 프로브가 `new Worker(name, handler, { connection: { url: requireEnv('REDIS_URL') } })`로 실제 잡을 처리시켜 확인했다. URL을 host/port/password로 쪼개지 마라. `{ url }`을 넘기면 **커넥션의 수명은 BullMQ가 소유하므로** 우리가 따로 `quit()`을 부를 대상도 없다(종료는 Task 5에서 `worker.close()`가 맡는다). 그래서 이 함수는 인스턴스가 아니라 옵션을 돌려준다 — 얇지만, 큐와 워커가 같은 옵션을 쓰게 만드는 단일 지점이라는 것이 존재 이유다.

**아직 재지 않은 것 둘.** (1) `maxRetriesPerRequest: null`이 이 조합(`bullmq@6.3.4` + `ioredis@5.11.1`)에서 필요한지 — 프로브의 실행은 그것 없이 동작했지만, 워커를 오래 돌리는 경우까지 본 것은 아니다. (2) `rediss://`(TLS)가 같은 경로로 되는지. **둘 다 짐작하지 말고 확인한 뒤 결과를 보고하라.** 필요하다고 판명되면 옵션에 더하고 그 근거를 주석에 적어라.

```ts
/** 워커 프로세스 설정. API는 이 값을 읽지 않는다. */
export interface WorkerSettings {
  readonly redisUrl: string;
  readonly refreshSessionRetentionSeconds: number;
}

/**
 * 워커 설정을 환경에서 읽는다.
 *
 * `REDIS_URL`은 워커에만 필수다(스펙 12장). API 프로세스는 이 함수를 부르지 않으므로
 * Redis 없이도 뜬다 — 그 분리가 "API는 broker를 import하지 않는다"는 계약의 절반이다.
 *
 * 보존 기간이 0인 것은 "만료되는 즉시 지운다"는 정상 설정이라 허용하고, 음수는
 * "미래의 행도 지운다"는 뜻이 되어 아직 유효한 세션을 지우므로 거절한다.
 */
export function loadWorkerSettings(env: NodeJS.ProcessEnv = process.env): WorkerSettings {
  return {
    redisUrl: requireEnv('REDIS_URL', env),
    refreshSessionRetentionSeconds: optionalNonNegativeInteger(
      'REFRESH_SESSION_RETENTION_SECONDS',
      604800,
      env,
    ),
  };
}
```

`src/config/broker.ts`는 findings의 연결 조각을 그대로 옮겨 쓴다. 파일 머리 주석에 다음을 남긴다 — **왜 `@nestjs/bullmq`가 아닌가**(실측: `AppModule` 그래프에 Bull 등록이 들어가면 `app-factory.ts` 때문에 스위트 전체가 Redis를 요구하게 된다), 그리고 **이 파일을 `src/config/app.module.ts`에서 import하면 그 계약이 깨진다**는 것.

### Task 4: `purgeExpiredRefreshSessions` 핸들러

**Files:**
- Create: `src/app/jobs/purge-expired-refresh-sessions.ts`
- Test: `test/integration/purge-refresh-sessions.spec.ts`
- Test: `test/integration/purge-refresh-sessions-contention.spec.ts`

**Interfaces:**
- Produces:
  ```ts
  export interface PurgeOptions {
    readonly retentionSeconds: number;
    readonly batchSize: number;
    readonly lockTimeoutMs: number;
  }
  export interface PurgeResult { readonly deleted: number; readonly batches: number }
  export function purgeExpiredRefreshSessions(dataSource: DataSource, options: PurgeOptions): Promise<PurgeResult>;
  ```

**`DataSource`를 받는 이유:** 배치마다 **커밋**해야 한다(스펙 10장). 한 트랜잭션으로 전부 지우면 긴 잠금이 걸리고 중간에 실패하면 한 행도 못 지운다. 배치마다 커밋하면 실패해도 이미 지운 것은 남고 재시도가 이어서 한다. 그러려면 함수가 트랜잭션을 **소유**해야 하므로 `EntityManager`가 아니라 `DataSource`를 받는다 — 이 저장소의 다른 함수들과 반대인데, 이유가 이것이라 주석에 남긴다.

**`lock_timeout`이 필수인 이유(실측):** `SKIP LOCKED`는 **자기가 고른 행**의 잠금만 피한다. `replaced_by_id`의 `ON DELETE SET NULL` cascade는 **다른 행**을 잠그는데 그 잠금은 `SKIP LOCKED`가 막아 주지 않는다 — 프로브가 500ms `lock_timeout`으로 55P03을 유도해 확인했다. 그래서 각 배치는 짧은 `lock_timeout` 아래에서 돌고, 경합하면 실패해 재시도에 맡긴다.

**동작이 확인된 문장:**
```sql
SET LOCAL lock_timeout = '500ms';
DELETE FROM refresh_sessions WHERE id IN (
  SELECT id FROM refresh_sessions WHERE expires_at < $1
  ORDER BY expires_at FOR UPDATE SKIP LOCKED LIMIT $2
) RETURNING id;
```

**`SET LOCAL lock_timeout`에는 파라미터 자리표시자를 쓸 수 없다.** 값을 문자열로 만들어 넣어야 하므로, **`lockTimeoutMs`가 음이 아닌 정수인지 먼저 확인하고 아니면 `TypeError`를 던져라.** 검사 없이 문자열을 이어 붙이면 그 자리가 SQL 주입 표면이 된다. 이 함수의 인자는 설정에서 오지 사용자에게서 오지 않지만, 그 사실은 호출자가 바뀌면 바뀐다.

- [ ] **Step 1: 롤백 안에서 확인할 수 있는 계약을 쓴다**

`test/integration/purge-refresh-sessions.spec.ts`. 이 스펙은 커밋하지 않는다 — **다만 함수가 배치마다 커밋하므로 `withRollback` 안에서는 그 커밋이 바깥 트랜잭션에 흡수된다.** 그래도 "무엇을 지우고 무엇을 남기는가"는 확인할 수 있다. 구현할 때 실제로 그렇게 도는지 확인하고, `DataSource`를 받는 함수라 롤백 픽스처와 맞지 않으면 **이 스펙 전체를 커밋하는 스위트로 옮기고 그 이유를 보고하라.**

고정할 계약:

- 보존 기간보다 오래 만료된 행만 지운다. 보존 기간 안에 있는 만료 행은 남는다. 아직 만료되지 않은 행도 남는다. (세 행을 만들어 한 번에 확인한다.)
- **오래된 순서로 지운다.** `batchSize: 1`로 한 배치만 돌렸을 때 가장 오래된 것이 사라져야 한다 — `ORDER BY expires_at`이 빠져도 전부 지우는 테스트로는 안 잡힌다.
- `batchSize: 1`에 만료 행 3개면 `batches`가 3이고 `deleted`가 3이다. 배치가 실제로 여러 번 돈다는 증거다.
- 지울 것이 없으면 `deleted: 0`, `batches`는 한 번(빈 배치를 보고 멈춘다).
- `lockTimeoutMs`가 정수가 아니면 `TypeError`.
- **폐기된 세션을 가리키던 `replaced_by_id`가 `null`이 되고 가리키던 행 자체는 남는다.** cascade가 실제로 `SET NULL`로 도는 것을 이 잡의 경로에서도 확인한다.

- [ ] **Step 2: 경합 계약을 별도 스위트로 쓴다**

`test/integration/purge-refresh-sessions-contention.spec.ts`. **이 스위트는 커밋한다** — 서로 다른 두 커넥션이 같은 행을 봐야 잠금 경합이 성립하고, 단일 트랜잭션 안에서는 원리상 만들 수 없다. Phase 6의 `refresh-session-concurrency.spec.ts`가 정확히 같은 이유로 같은 모양을 하고 있으니 그 파일을 읽고 관용구를 따르라.

지켜야 할 규율:

- 이 스위트만의 이메일 접두사를 쓰고 그것만 지운다(사용자를 지우면 세션은 `ON DELETE CASCADE`로 따라간다). 지금 커밋하는 다섯 스위트의 접두사(`auth-`, `me-`, `examples-api-`, `examples-put-`, `refresh-concurrency@example.test`)와 겹치지 않는 것을 고른다.
- `TRUNCATE`도 조건 없는 `DELETE`도 쓰지 않는다.
- `acquireCommitLock`은 잡지 않는다 — 다만 **판단해서 정하고 이유를 주석에 남겨라.** 지금 여섯 스위트가 `users`/`refresh_sessions`에 커밋하고, 이 스위트는 그중 유일하게 **스코프 없이 만료 행을 지우는** 함수를 부른다. 다른 스위트가 커밋해 둔 세션이 이 잡의 삭제 대상에 들어갈 수 있는지 따져 보라 — 들어갈 수 있다면 접두사 분리로는 부족하고 잠금이 필요하다. **이것이 이 태스크에서 가장 놓치기 쉬운 지점이다.**

고정할 계약 둘:

- **다른 트랜잭션이 잡고 있는 만료 행은 건너뛴다**(`SKIP LOCKED`). 잠긴 행 하나와 안 잠긴 만료 행 하나를 두면, 한 배치가 안 잠긴 것만 지우고 잠긴 것은 남긴다.
- **cascade 경합에서는 실패한다.** 다른 트랜잭션이 `replaced_by_id`로 가리키는 행을 잠근 채 두면, 짧은 `lock_timeout` 아래의 배치가 55P03으로 실패해야 한다 — 매달리지 않는다. 실패가 재시도에 맡겨진다는 것이 스펙 10장의 의도다. **테스트가 매달리지 않도록 순서를 결정적으로 짜라**(Phase 6의 동시성 스펙이 A를 커밋해 B를 풀어 주는 순서를 쓴 것과 같은 종류의 주의가 필요하다).

**레드를 실측하라.** `SKIP LOCKED`를 빼면 첫 계약이, `SET LOCAL lock_timeout` 줄을 빼면 둘째 계약이 실제로 깨지는지 각각 확인하고 원복한 뒤 보고서에 적어라. 이 저장소는 동시성 테스트가 실은 아무것도 검증하지 않던 사례를 두 번 겪었다.

- [ ] **Step 3: 구현한다**

`src/app/jobs/purge-expired-refresh-sessions.ts`. 루프는 "빈 배치를 만날 때까지"이고, 각 배치는 자기 트랜잭션 안에서 `SET LOCAL lock_timeout` → 위 `DELETE ... RETURNING id`를 돌린다. 반환된 행 수가 `batchSize`보다 적으면 마지막 배치다.

**무한 루프 방어를 반드시 넣어라.** `SKIP LOCKED`가 잠긴 행을 계속 건너뛰면 같은 배치가 0행을 돌려주며 끝나지만, 구현이 어긋나면 같은 행을 영원히 고를 수 있다. 배치 수 상한을 두고 넘으면 경고와 함께 멈춘다 — 워커를 영원히 붙잡는 잡보다 낫다.

주석에 남길 것: 왜 `DataSource`인가(배치 커밋), 왜 `lock_timeout`이 필수인가(실측 근거와 함께), 왜 실패를 삼키지 않는가(재시도에 맡긴다), `SET LOCAL`에 자리표시자를 못 써서 정수 검사를 먼저 한다는 것.

### Task 5: 큐와 워커 진입점

  ```ts
  export function enqueueProcessExample(queue: Queue, payload: ProcessExamplePayload): Promise<Job>;
  export function enqueuePurgeExpiredRefreshSessions(queue: Queue): Promise<Job>;
  ```

**워커가 Nest 컨텍스트를 만들지 않는 이유:** HTTP도 컨트롤러도 필요 없고, `AppModule`을 부팅하면 API의 설정 요구(`JWT_SECRET_KEY` 등)까지 워커가 지게 된다. `src/config/data-source.ts`가 이미 `DataSource`만 직접 만드는 법을 보여 주고 있으니 그 방식을 따른다.

**graceful shutdown은 실측된 세 줄이다.** `worker.close()`가 이미 "진행 중인 잡이 끝날 때까지 대기"를 구현하고 있다 — 프로브가 1.5초짜리 잡 중간(300ms 시점)에 `close()`를 불러 남은 1200ms를 정확히 기다린 뒤 반환하는 것을 쟀다. `{ url }`로 연결을 넘기면 커넥션은 BullMQ가 소유하므로 따로 닫을 대상이 없다.

```ts
process.on('SIGTERM', async () => {
  await worker.close();
  await dataSource.destroy();
  process.exit(0);
});
```

`SIGINT`도 같이 붙인다(로컬에서 Ctrl+C로 세우는 경로다). **프로브가 남긴 한계도 같이 옮겨 적어라** — 아주 긴 잡이 `SIGTERM` 뒤에도 끝나지 않으면 이 핸들러는 무한정 기다린다. 강제 타임아웃을 넣을지는 판단해서 정하되, 넣지 않기로 했다면 그 사실과 이유를 주석에 남겨 다음 사람이 "빠뜨린 것"으로 읽지 않게 하라.

- [ ] **Step 1: 실패하는 통합 테스트를 쓴다**

`test/integration/jobs-queue.spec.ts`. 실제 Redis와 실제 PostgreSQL을 쓴다(Task 2가 게이트에 Redis를 넣었다).

고정할 계약:

- **enqueue한 잡이 `attempts: 3`으로 들어간다.** 스펙 10장의 재시도 계약이 enqueue 지점에 실제로 실려 있는지를 본다 — 큐에 넣은 `Job`의 옵션을 그대로 읽어 단언한다.
- **워커가 실제로 잡을 집어 처리한다.** 진짜 Example을 하나 만들고 `processExample`을 enqueue한 뒤 워커를 띄워 완료를 기다리고, 행이 바뀌지 않았는지까지 확인한다.
- **던지는 프로세서는 정확히 세 번 불린다.** 이 테스트만을 위한 별도 큐 이름과 던지는 프로세서를 써서, `attempts: 3`이 "총 세 번의 시도"를 뜻한다는 것을 실측으로 고정한다(프로브가 잰 것과 같은 값이어야 한다). backoff를 짧게 줘서 테스트가 오래 걸리지 않게 한다.
- **테스트가 쓰는 큐는 테스트가 지운다.** 실제 Redis를 공유하므로, 스위트마다 고유한 큐 이름 접두사를 쓰고 `afterAll`에서 `queue.obliterate({ force: true })`(또는 findings가 확인한 방법)로 지운다. **다른 스위트나 개발자의 Redis 키를 지우는 넓은 삭제(`FLUSHALL` 등)를 절대 쓰지 마라** — `TRUNCATE`를 금지하는 것과 같은 이유다.
